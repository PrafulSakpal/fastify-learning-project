# JSON Schema

## What is it?

A JSON-based way to describe the shape of data — required fields, types,
formats, enums, string patterns — that Fastify attaches to a route via the
`schema` option, for `params`, `querystring`, `body`, `headers`, and
`response`.

## Why does Fastify have it?

Two problems, solved by the same mechanism:

1. **Input validation** — reject malformed requests before they ever reach
   your handler, with an autogenerated 400 (see [14-validation.md](14-validation.md)).
2. **Output serialization** — turn your handler's return value into JSON
   using a schema-compiled, much faster serializer than `JSON.stringify`,
   while also enforcing exactly which fields are allowed out
   (see [15-serialization.md](15-serialization.md)).

Because schemas are known upfront (at route registration, before any
request arrives), Fastify compiles both the validator and the serializer
**once at startup**, instead of re-interpreting the schema on every request.

## How does it work?

```typescript
app.get('/appointments/:id', {
  schema: {
    params: {
      type: 'object',
      required: ['id'],
      properties: { id: { type: 'string', minLength: 1 } },
    },
    response: {
      200: { type: 'object', properties: { id: { type: 'string' } /* ... */ } },
      404: errorResponseSchema,
    },
  },
}, async (request, reply) => { /* ... */ });
```

### Getting TypeScript types from the schema, not the other way around

Writing a JSON Schema and a separate TypeScript interface for the same data
is a maintenance trap — they drift. This project uses
`@fastify/type-provider-json-schema-to-ts` so the **schema is the single
source of truth**, and `request.params`/`query`/`body` and the response
shape are all inferred from it automatically:

```typescript
// src/app.ts
const app = Fastify({ logger: true }).withTypeProvider<JsonSchemaToTsProvider>();
```

```typescript
// src/modules/appointments/appointment.routes.ts
export const appointmentRoutes: FastifyPluginAsyncJsonSchemaToTs = async (app) => {
  app.get('/appointments/:id', { schema: getAppointmentSchema }, async (request) => {
    request.params.id; // typed as `string` — inferred, not hand-written
  });
};
```

This only works if every schema object is declared `as const` (see
[appointment.schemas.ts](../../src/modules/appointments/appointment.schemas.ts))
— without it, TypeScript widens `type: 'object'` to the general `string`
type and the inference falls apart.

## Simple example

```typescript
const bodySchema = {
  type: 'object',
  required: ['name', 'email'],
  properties: {
    name: { type: 'string' },
    email: { type: 'string', format: 'email' },
  },
} as const;

app.post('/subscribe', { schema: { body: bodySchema } }, async (request) => {
  return { received: request.body.email }; // typed as string
});
```

## Application example

[src/modules/appointments/appointment.schemas.ts](../../src/modules/appointments/appointment.schemas.ts)
holds every schema for this module — one file, so all of a resource's
input/output contracts are visible together. For example, `date` and
`startTime` use `format` and `pattern` respectively:

```typescript
export const createAppointmentBodySchema = {
  type: 'object',
  required: ['userName', 'serviceName', 'date', 'startTime'],
  additionalProperties: false,
  properties: {
    userName: { type: 'string', minLength: 1 },
    serviceName: { type: 'string', minLength: 1 },
    date: { type: 'string', format: 'date' },        // e.g. "2026-10-01"
    startTime: { type: 'string', pattern: '^([01]\\d|2[0-3]):[0-5]\\d$' }, // "HH:MM"
  },
} as const;
```

Verified against the running app:

```bash
curl -X POST http://localhost:3000/appointments \
  -H "Content-Type: application/json" \
  -d '{"userName":"Sam","serviceName":"Massage","date":"not-a-date","startTime":"09:00"}'
# {"success":false,"error":{"code":"VALIDATION_ERROR","message":"Request validation failed",
#   "details":[{"field":"/date","message":"must match format \"date\""}]}}
```

## Important details

- Fastify uses **AJV** under the hood, with its own default options (see
  [@fastify/ajv-compiler's defaults](../../node_modules/@fastify/ajv-compiler/lib/default-ajv-options.js)):
  `coerceTypes: 'array'`, `useDefaults: true`, `removeAdditional: true`,
  `allErrors: false`. Every one of these has a real, visible effect covered
  in [14-validation.md](14-validation.md) and [15-serialization.md](15-serialization.md)
  — don't assume AJV's own defaults apply; Fastify overrides them.
- `format: 'date'`/`'email'`/etc. work out of the box because Fastify
  depends on `ajv-formats` directly — no extra install needed.
- The `response` schema is keyed by **status code**: `response: { 200: ..., 404: ... }`.
  A status code with no matching schema key is sent as plain JSON, unvalidated
  and unfiltered.

## Common mistakes

- Writing a schema without `as const` and wondering why `request.body` is
  still typed as `any`/`unknown` — the type provider needs the literal type.
- Forgetting `additionalProperties: false` and assuming unexpected fields in
  the body are rejected — with Fastify's default AJV options they are
  silently **stripped**, not rejected (see [14-validation.md](14-validation.md)).
- Defining the schema once and then still writing a hand-rolled TypeScript
  interface for the same shape "just in case" — pick one source of truth.

## Best practices

- Keep all of a module's schemas in one `*.schemas.ts` file, next to its
  `*.routes.ts` file.
- Always give response schemas a `required` list and `additionalProperties: false`
  when you want a clean, fully-typed shape instead of an "everything optional"
  inferred type.
- Reuse shared schemas (like `errorResponseSchema`) across modules instead of
  redefining the same error shape per resource.

## Express comparison

Express has no built-in schema concept — validation is typically bolted on
via a separate library (`joi`, `zod`, `express-validator`), each with its
own syntax, and response shaping is manual (`res.json({...})` with whatever
fields you remembered to include or omit). Fastify's JSON Schema is native,
one format for both validation and serialization, and — with a type
provider — also drives compile-time types.

## Interview questions

1. What is JSON Schema used for in Fastify, specifically (two purposes)?
2. Why are schemas compiled once at startup instead of per-request?
3. How does this project get TypeScript types for `request.body` without
   writing a separate interface?
4. What does `additionalProperties: false` actually do under Fastify's
   default AJV configuration — reject, or something else?

## Interview answer

> In Fastify, a JSON Schema attached to a route serves two purposes: Fastify
> compiles it once, at startup, into both a fast validator (for
> params/querystring/body/headers) and a fast serializer (for the response).
> This project also uses `@fastify/type-provider-json-schema-to-ts` so the
> schema — written `as const` — is the single source of truth for
> `request.params`/`query`/`body`'s TypeScript types too, instead of
> maintaining a parallel hand-written interface that can drift out of sync.
> Fastify layers its own default AJV options on top of plain AJV, which
> changes some default assumptions — notably that unexpected properties are
> stripped rather than rejected unless you test for that specifically.
